# AI Usage

AI tools were used to accelerate this assignment. This file records what was used
and where, per the brief.

## Tools used

- **Kiro (AI coding assistant)** — the primary tool. Used to scaffold the
  project, draft the backend and frontend, and generate the initial tests and docs.

## What I used it for

- **Scaffolding**: initial directory layout, `package.json`/`tsconfig`, Docker
  and compose files.
- **Boilerplate**: the Express route wiring, the Knex repository, the React pages
  and CSS.
- **Tests**: the first pass of the Jest suite covering the six required scenarios.
- **Docs**: first drafts of this README's engineering answers and the Graphviz
  architecture diagram source.

## Significant code/design generated by AI

- The `documents` / `document_history` schema and the repository layer.
- The atomic "claim next document" transaction in the worker.
- The mock processor with keyword/scripted outcome control for deterministic tests.
- The React upload/list/detail pages and the timeline rendering.

## What I changed or rejected after reviewing the output

- **Type error in the list query.** The generated `listDocuments` used
  `.count<{...}>()` type arguments on an `any`-typed query chain, which does not
  compile (`TS2347`). I removed the type arguments and cast the result instead.
- **Broken smoke-test assertion.** An initial live smoke test asserted
  `history[0] === 'UPLOADED'` against the raw history objects (which are
  `{status, attempt, reason, timestamp}`), not status strings. The app was
  correct; the assertion was wrong. I fixed it to map to `.status` first. This is
  a good example of *not* trusting AI output blindly — the code "looked right" and
  the pipeline genuinely worked; only running it surfaced the test bug.
- **Retry policy for INVALID_RESULT.** The first cut treated every non-success
  outcome as retryable. I changed it so only `TIMEOUT`/`ERROR` (transient) are
  retried; `INVALID_RESULT` and validation failures go straight to terminal
  `FAILED`, because retrying a deterministic data problem just wastes attempts.
- **Duplicate handling response.** I settled on returning the *existing* document
  with `duplicate: true` and HTTP 200 (idempotent) rather than a 409 error, since
  the brief frames duplicates as "identify", not "reject".

## What I learned / verified while reviewing AI output

- The most valuable check was **running the code**, not reading it: the type
  error and the test-assertion bug were both invisible on inspection and obvious
  on execution. I verified the full pipeline end to end against a live server
  (upload → PROCESSING → PROCESSED, history, stats, duplicate) and via the
  deterministic Jest suite before considering it done.
- I made the processor outcomes controllable (by filename and by an in-test
  script) specifically so the retry and failure paths could be tested
  deterministically — random failure rates make flaky tests.
